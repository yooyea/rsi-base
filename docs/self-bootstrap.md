# rsi-base 自举

指导项目通过「可靠的工程化」保障自我迭代，首先要对本仓库成立。
这里的自举是：用本仓库准则识别自身风险、建立保障、验证有效性，
让后续修改继续受到保障。不是宣称能够无人授权地持续运行或自主合并。

## 自身保障与适用边界

| 自身风险 | 已实现的工程载体 | 可验证范围与限制 |
| --- | --- | --- |
| 入口或本地链接失效 | [文档检查器](../scripts/check_docs.py) | 简单内联本地链接；不检查外部链接、锚点及引用式链接。 |
| 新准则遗漏约定结构或无法被找到 | 同一检查器递归扫描准则、检查必需正文及从 SKILL 的可达性 | 接受正例，拒绝空章节、孤立及深层遗漏准则；不判断内容有无价值。 |
| 检查器被改坏 | [检查器反例测试](../tests/test_check_docs.py) | 包含错误变更失败、修复通过；代表性案例不等于完备证明。 |
| 平台规则与仓库约定漂移 | [期望规则](../.github/rulesets/main.json)与[只读审计器](../scripts/check_repository_rules.py) | 读不到完整配置就失败；该在线审计不在普通文档 CI 中运行。 |
| 未完成检查被当成可合入 | [Documentation 工作流](../.github/workflows/docs.yml)与实际 GitHub 规则集 | 必需状态来自 GitHub Actions，严格基线检查，无旁路名单；配置和真实行为分别验证。 |
| 验证时悄悄改变交付内容 | 同一工作流检查 Git 工作区 | 约束已跟踪和未忽略的新文件，不等于通用可复现构建。 |
| 中断后不知道哪些真正完成 | PR 的版本、检查、阻断演练与剩余缺口记录 | 新会话从仓库及 PR 恢复，不把历史记录当作当前结果。 |

## 变更时怎样使用自己的准则

按 [SKILL.md](../SKILL.md)进入相关准则，复用上述入口。新缺陷先证明现有检查
漏过了什么，再补相应反例与修复。每次变更执行离线测试和文档检查。

涉及工作流、检查器、预期规则或平台规则时，说明保障是否变化，并执行只读在线审计。
必要时重复隔离分支阻断实验。不能删除检查、增加旁路或放宽约定来让当前变更过关。
普通编码任务不获得管理员权限；平台配置修改只能在用户明确授权下进行。

```sh
python3 -m unittest discover -s tests -v
python3 scripts/check_docs.py
python3 scripts/check_repository_rules.py --repository yooyea/rsi-base
```

最后一项需要 GitHub CLI 的只读查询能力及可见完整旁路配置的身份。
它只有读取操作，不会安装或修改规则，也不能代替真实合入实验。

## 如何证明门禁生效

在隔离的临时目标分支上使用同一个有效规则集、同一个必需状态和同一个执行身份。
构造不存在的文档链接，确认检查失败；通过正常合并 API 提交请求，记录拒绝原因并
确认目标 SHA 未变。然后修复同一反例，重新检查，并验证正常合入。

实验不能拿主干冒险。结束后移除临时规则匹配和临时分支，确认主干约束仍与仓库期望一致。
具体 SHA、PR、运行和 API 结果放在 PR 记录；只做静态核对时明确标记未做阻断实验。

## 不夸大保障

单人仓库不伪造第二个审查者，当前不要求独立 GitHub approval。
用户对定位与本次自举的确认不是以后任意敏感变更的永久授权。
管理员仍然能修改平台规则；本次不声称已经建立独立于管理员凭据的防篡改控制面。
对准则语义、复杂度、外部来源及实际指导效果的审查，仍需结合具体内容与用户目标。
文档检查通过，不等于这些方面已由机器证明。
